# Explain automated-workflow outcome integrity

## Identity

- ID: automation-outcome-focused-learning
- Kind: application

## Covered objects

- [Automation Handbook](../../SKILL.md)

## Protected behavior

A focused request to understand whether an automated workflow's reported result
honestly represents its required work must read the matching foundation subject
without forcing unrelated recovery, diagnostic-evidence, or Git-comparison
material. Protect direct foundation-subject learning and application while
allowing different explanation structures and examples.

## Task

Explain how a CI/CD workflow can report success even though required validation
was skipped, missing, cancelled, or never produced usable evidence. Describe how
the workflow's completion contract should distinguish a genuinely
non-applicable check from incomplete execution, and how a final gate should
prevent protected work from depending on absent successful evidence. This is a
focused explanation; do not design, modify, or review a concrete workflow.

## Starting state

Supply the complete current Automation Handbook, its permitted direct canonical
routes, and the natural task request. Do not supply this case, expected reading
choices, evaluator criteria, prior outputs, or author conclusions. Use a fresh
supported lower-capability model with the expanded executor guard, read-only
access to the supplied repository snapshot, and a six-minute wall-clock
allowance.

Ask the executor to record every selected and excluded reading unit before
opening Knowledge, then answer the task. Record the exact source snapshot,
model, configuration, reading choices, files read, final answer, and available
action observations.

## Expected behavior

- R1 (critical): select and read [Outcome integrity in automated
  workflows](../../../../knowledge/automation/workflow-outcome-integrity.md).
- R2 (critical): exclude operation-failure-and-recovery,
  failure-diagnostic-evidence, and Git change-comparison reading because no
  concrete automation artifact, recovery question, investigation-evidence
  question, or revision comparison is present.
- R3: explain that applicability must be established successfully and kept
  separate from execution, while failure, cancellation, timeout, unexpected
  skipping, and missing results cannot satisfy a required-success contract.
- R4: bind the final accepted status to every applicable required check and
  prevent protected effects from advancing on absent successful evidence.
- R5: keep the explanation supplemental to active requirements and state its
  evidence limits without inventing validation or platform behavior.

## Verification

Use the application dispatch template. Inspect Handbook reading choices, actual
file reads, and the explanation separately. Give the capable reviewer this
contract, the final Handbook and direct routes, and the raw observation without
the coordinator's verdict. Judge every criterion independently and retain every
attempt.

A controlled faulty observation that loads the complete primary-work
foundation, omits workflow outcome integrity, or treats a missing check as a
valid non-applicable result must fail the corresponding criterion. The
controlled copy calibrates the reviewer and is not another Agent run.

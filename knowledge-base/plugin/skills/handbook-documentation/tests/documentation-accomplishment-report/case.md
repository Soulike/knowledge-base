# Explain a verified engineering accomplishment

## Identity

- ID: documentation-accomplishment-report
- Kind: application

## Covered objects

- [Documentation Handbook](../../SKILL.md)

## Protected behavior

An engineering accomplishment report explains delivered change and its value
to a decision maker. It requires the accomplishment-report route without
forcing maintained-document or software-manual reading merely because the
output is prose about software. Protect evidence-based reporting while allowing
different concise structures and wording.

## Task

Prepare a short account for the engineering lead's next planning meeting of
what the command-line option rename accomplished and why it matters. Use the
supplied completion facts and make any remaining evidence limits clear.

## Starting state

Supply these established facts as independent task material:

- The CLI option changed from `--cache` to `--cache-dir`, making its directory
  operand explicit.
- The maintained setup guide, executable example, and source docstring now
  agree with the implementation.
- The documented command was executed successfully in a local environment.
- No production-use study or measured time saving is available.

Supply the complete current Documentation Handbook and its direct packaged
routes. Record package choices before Knowledge access. The task produces a
report in the response; no documentation edit or execution is requested. It
does not depend on running another case or inheriting its reading.

## Expected behavior

- D4 (critical): select and read engineering-accomplishment-report guidance
  through the Handbook's direct route, then apply it to a concise account for a
  decision maker.
- D5 (critical): exclude maintained-document-quality and software-development
  documentation reading; prose and a software topic alone do not activate them
  for this report-only request.
- D6: explain the delivered outcome and practical value from the supplied
  facts. Keep local verification distinct from production validation and avoid
  invented impact measurements or a mere list of author activities.

## Verification

Inspect the package choices, complete direct reading, and resulting report.
Check each material claim against the supplied facts. A correct report must
remain possible without source editing, prior-case outputs, or the maintenance
packages.

## Source

[GitHub issues #242](https://github.com/Soulike/knowledge-base/issues/242) and
[#247](https://github.com/Soulike/knowledge-base/issues/247) distinguish
engineering reports from maintained software documentation. This case retains
D4–D5 from the formerly combined
[documentation case](../documentation-stage-change/case.md), with explicit
independent completion facts and evidence limits. The maintainer accepted the
split because topic and chronology alone did not establish a connection
contract between maintenance and reporting.

# Probe web usability risks with Agents

Produce an evidence-backed analysis of an interactive web task path. The probe ends with a risk report; decisions and work to change the interface belong to the calling task.

1. Follow instructions, requirements, and safe-operation constraints from the active project. Read [Task-based usability observation](../../knowledge/user-interface/task-based-usability-observation.md) and [Evidence from Agent usability risk probes](../../knowledge/user-interface/agent-usability-evidence.md) as supplemental guidance. Locate the interactive prototype or site and the task path to inspect. For a static mockup or native app, explain that this workflow cannot execute its task path and stop.
2. Establish a small set of meaningful tasks from user goals, product requirements, or existing use evidence. Mark unsupported candidate tasks as hypotheses. For each task, state the goal, minimum relevant domain and device context, starting state, and an independently observable completion criterion. Keep intended clicks and design rationale out of the tester's brief. If a completion criterion cannot be established, ask for one and stop before running that task.
3. Confirm access to a safe environment, suitable test accounts and data, and a way to restore or isolate starting states. If no safe test environment is available, stop and ask the user how to proceed before interacting with the interface, especially where a path could submit, purchase, send, or alter real data. Record the interface revision, environment, and permitted operations so later observations can be attributed to the tested state.
4. Plan bounded runs across the selected tasks and set an action or time limit before each run. For each critical task, plan a visual screen-driven run and a separate semantic run that exercises keyboard navigation. Use a reliable browser-capable model for the baseline; add a less capable model that still has the needed modality and tools as a comparison, choosing task-channel pairs that expose the main uncertainties. Select models by relevant browser-task capability rather than price or name alone. Keep task, data, viewport, and entry state comparable within each pair. Repeat a run only to clarify an unstable or suspicious observation. If a channel, keyboard control, or suitable comparison model is unavailable, record the specific coverage gap rather than treating another channel or model as equivalent.
5. Give each tester only its task brief, necessary credentials, and the allowed browser controls. Isolate it from source code, design notes, the intended route, other testers' traces, and the completion evaluator's judgment. In the visual run, choose actions from rendered screens; in the semantic run, choose from accessible semantics and exercise the critical route with keyboard controls. Do not label a run visual because a screenshot was captured if actions were chosen from the accessibility tree. Record the channel, model, screen or accessibility state, a short expectation before consequential actions, the action, and the observed response. Keep generated explanations separate from behavior. Stop a run when the interface presents apparent completion, at an unsafe boundary, or at a preselected action or time bound; record which condition ended it instead of attributing a model stall to human frustration.
6. In an evaluator context separate from the tester, or through a deterministic check outside its self-report, compare the resulting page or system state and relevant raw trace with the predeclared completion criterion. Do not accept a tester's self-report or a success message as proof of an unobserved state change. If the criterion unexpectedly cannot be checked, stop the affected analysis and ask for a verifiable criterion. Preserve browser or tool failures separately from interface behavior.
7. Compare baseline and lower-capability results, and visual and semantic results, without pooling them into a synthetic user count. For each suspected risk, identify the observed action and interface evidence, the task consequence, recovery cost, plausible alternative explanations, and confidence. Treat a lower-capability-only failure as a lead until the interface evidence supports it. Rank findings by task impact, error consequence, recovery cost, and evidence quality; do not interpret run counts as a human occurrence rate. Flag questions that warrant real-user evidence because the consequence or uncertainty remains material.
8. Report the tested task and its evidence or hypothesis basis, context, interface revision, model and channel coverage, independently checked result, concise trace or artifacts, prioritized risks, alternative explanations, and limitations. Distinguish blocked or unverified tasks from completed probes. Finish when every selected task has a verified result or an explicit stop reason and every reported risk is traceable to an observation. End the Skill at the analysis; any repair or later retest is a separate decision by the calling task.

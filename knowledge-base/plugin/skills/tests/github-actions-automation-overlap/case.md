## Protected behavior

General automation and GitHub Actions independently own overlapping reading
scenes. Protect their direct foundations, cumulative platform packages, and
engine-specific conditions without changing the execution engine mid-task.

## Task

Consider two independent designs, both known from the start:

1. Design a GitHub Actions pull-request workflow that checks out the current
   PR head, sets up its runtime, lets an Agent inspect it, and posts the decision
   as a PR comment. Rerun when the head changes; later jobs must not publish or
   act on stale, failed, or incomplete results. No gh-aw engine is specified.
2. Design that workflow for gh-aw's Copilot engine. Explain the additional
   runtime, authentication, and model prerequisites and remaining limits.

Do not publish a workflow or comment.

## Starting state

Supply all requests and necessary task facts up front, the complete current
covered guidance, and normal read-only access to its direct packaged routes.
Use a fresh supported lower-capability model with the expanded executor guard
and a task-appropriate bounded allowance established before dispatch. Keep the
case, expected choices, previous outputs, and evaluator discussion private.

Before opening Knowledge, record selected and excluded reading units separately
for each independent request. Then permit the union of required direct reads
and perform the tasks. Record source identity, model/configuration, choices,
actual file or section reads, outputs, and action limits. The per-request
choices test domain conditions; a shared executor's union of reads does not
prove that a document was never loaded in another request. Do not stage a task
change or score reassessment, reading reuse, or rereading in this case.

Supply the [controlled current platform inputs](fixtures/verified-platform-inputs.md)
as ordinary task facts for permission and version decisions. Do not require
external retrieval to replace those controlled facts. Make the maintenance
Catalog unavailable as a runtime route.

## Expected behavior

- R1 (critical): both designs use the independently applicable Automation and
  GitHub Actions Handbooks; neither is a dependency of the other.
- R2 (critical): read the complete automation and GitHub Actions foundations
  through their direct canonical routes. Their outcome-integrity links refer
  to the same canonical document.
- R3 (critical): both contexts match permissions, version-selection, and
  Agent-run-state packages cumulatively. Do not assign gh-aw compatibility to
  request 1, where that execution path is absent.
- R4: use the controlled facts for permissions and pins; bind accepted results
  and effects to immutable PR/head/run-attempt identity and honest completion
  evidence, and state limits not established by the platform contract.
- R5 (critical): request 2 also matches the gh-aw Copilot compatibility package.
  Apply it before claiming an executable design; report missing runtime, auth,
  model, or capability facts instead of inventing compatibility.
